# InfiniLM V3 有界等待缓存副本实验

这是基于已经在 MUSA 跑完的长度实验制作的优化候选。V3 尚无 GPU 性能结果。只有真实同轮结果才能决定是否替换 V2。入口为 `run_optimized.sh`，本包中的旧入口仅用于保留原始来源与回归测试。

## 改动依据

来源为 `lengths_run_c16_20261103T084528_757875Z_report.zip`。其 8192 输入的两组 V2 正式测试有 26 条实际缓存命中为零的请求，其中 12 条在其他卡上存在观测到的完整缓存，但这些卡均已达到每卡 3 个请求的硬上限。12 条中有 3 条仅在非 owner 卡上有完整缓存。历史日志未保存这些候选卡当时逐请求的剩余输出量，因此无法从历史数据证明等待多久最合适。

两条完整命中仍超过 4 秒的请求前面有 pending prefill，即同卡尚未开始输出的请求。已有日志没有证明它们存在可立即切换的更快副本。本候选通过尝试减少冷输入计算，间接减轻这类等待，没有修改 GPU 内核或后端调度器。

## V3 的具体行为

V3 继承原 `cache_router.Router`，新文件为 `cache_router_v3.py`。改动集中在准入前的等待决策。除了原先重点考虑的 owner，也检查其他健康副本，只有对同一前缀有有效完整缓存观测，或存在已经开始输出的相同前缀请求，而且该卡没有 pending prefill，才作为等待候选。后者只是复用预测，绝不记作已经命中。

候选必须暂时被硬容量挡住，且最早完成的一个请求释放后足以容纳新请求。用既有独立校准模型估算最早释放时间，再加命中后的输入处理成本，与立即分配方案比较。预计节省不足时直接沿用 V2 的分配结果。等待期间持续重新检查，每次都使用一个固定截止时间，不能刷新延长。

| 参数 | 本次固定值 |
|---|---|
| 新策略等待预算上限 | 1000 ms |
| 实际等待预算 | min(1000 ms, 校准的冷/热输入成本差 × 25%) |
| 值得等待的成本差 | 大于 max(2 ms, 上述冷/热成本差 × 5%) |
| 候选显卡 | 健康、存在复用依据、无 pending prefill、暂时被硬容量挡住 |
| 每卡最大在途请求 | 3，继承原配置 |
| KV 预留 | 每个请求完整预留输入加最大输出，再按 256 token 对齐 |
| 每卡 KV 总容量 | 32768 token，继承原配置 |
| 缓存快照有效期 | 5 秒，继承原配置 |
| 公平性 | 被后面的请求越过 8 次后停止此等待，继承原规则 |

1000 ms、25% 和 5% 是此次事先固定的候选参数，不是已经验证的最优值。V3 替换原等待条件，同时收紧了“候选没有 pending prefill”的要求，因此它并非原等待规则的简单并集。V3 不放宽原来的 count bound、显卡并发上限或 KV 上限。缓存副本只有空出容量后才能实际接收请求。预测与实际命中在记录中分开保存。

这个预算仅约束 V3 主动等缓存副本的决策。全局没有可用容量时仍执行原有排队规则，因此请求的总网关等待或首响应时间可能超过 1 秒，实际值全部计入结果。

## 测试设置

硬件、模型、HTTP 连接方式、计时、采样参数、缓存容量和执行生命周期均沿用成功包。模型为 Qwen3-32B BF16，8 张 MTT S5000，各自运行一个 TP1 完整副本。整体客户端并发固定 16，每卡上限 3，总后端上限 24。

| 场景 | 输入 token | 共享前缀 token | 输出 token | 文档数 | 热文档比例 |
|---|---:|---:|---:|---:|---:|
| p8192_o32 | 8192 | 7936 | 32 | 8 | 25% |
| p8192_o64 | 8192 | 7936 | 64 | 8 | 25% |
| p8192_o128 | 8192 | 7936 | 128 | 8 | 25% |

32 和 128 输出为前次已经有优势的配置。64 输出为两者之间新增的一组。三组复用同一批输入、文档顺序、请求 ID 和分词结果，只改变输出上限。8192/32 原始请求文件字节保持一致。生成请求会用服务器上的实际 tokenizer 校验。

固定 seed=33962，一轮，每个方法每组先执行 64 条学习请求，再执行 128 条正式请求。三种方法为 V3、原 V2、vLLM least-active，共 9 个测试单元、1728 条请求。三组长度之间轮换执行顺序，每种方法分别占一次第一、第二、第三位置。每个单元独立启动八副本模型池，学习阶段建立缓存，正式阶段继承该单元的缓存。

这是一轮固定种子的有利场景筛查。跨三种长度的位置平衡不能替代同一长度多次复测。仅展示这三个声明场景的结果，不代表所有工作负载。所有对照均现场重跑，不拿旧报告数字充当本轮测量。

## VS Code 终端运行

将 ZIP 上传到 `/mnt/zj-data/data/chengcp/infinilm/`，在原成功环境执行。新目录与原目录并存。

```bash
cd /mnt/zj-data/data/chengcp/infinilm
python3 -m zipfile -e infinilm_cache_v3_20261104.zip .
cd infinilm_cache_v3_20261104
bash run_optimized.sh plan
```

确认计划列出三组长度、三种方法、9 cells、seed 33962 和 1 round 后运行。

```bash
nohup bash run_optimized.sh run > optimized.log 2>&1 < /dev/null &
echo $! > optimized.pid
tail -f optimized.log
```

`Ctrl+C` 退出 `tail` 不会停止后台实验。请等待此作业结束后再启动其他占用这八张卡的实验。`run` 自动执行 CPU 回归检查、原环境检查、实际分词校验、校准、模型池测试和报告生成。默认解释器沿用原控制环境，可用 `CONTROLLER_PYTHON` 指向原已成功的控制端 Python。

如仅检查当前环境而不加载模型，可执行 `bash run_optimized.sh check`。这不会生成性能结果。失败时保留现场日志和打包报告，不自动重试失败推理或忽略缺失请求。

## 如何判断优化是否有效

主要看同一长度下正式阶段的输出吞吐，再同时看平均 TTFT、p95 和学习加正式阶段的合计结果。报告分别计算 V3 对原 V2、V3 对 vLLM 的差值。2% 作为实用差异参考，不作为统计显著性证明。无需把不同输出长度的 token/s 混在一起平均。

诊断重点为实际缓存命中为零的请求数、完整前缀命中数、等待 4 秒以上的请求数、分配时同卡 pending prefill 数，以及 V3 有界等待的次数、时长、最终去向和实际命中结果。vLLM 未返回的缓存信息保留未知，不能记作零命中。

如果等待减少了冷请求但吞吐下降，也必须保留这一结果。候选没有优势时继续保留 V2。脚本不自动调参、不删除失败场景、不自动追加实验。

完成后日志打印 `OPTIMIZATION_REPORT_ARCHIVE=`，后面是可上传的完整报告 ZIP 路径。主要结果见 `optimization_report.md` 和 `optimization_cases.csv`。`optimization_status.json` 表示整套流程是否完成，`optimization_report_status.json` 表示结果审计是否通过。旧的 `report.md` 与 `confirmation_*` 是辅助配对报告，性能解读优先使用新的优化报告。

`baseline_sources.json` 保存成功运行归档中 70 个已有 Python/Shell 源文件的 SHA256。这些文件在本包中保持字节一致。新增逻辑、运行器和报告代码独立放置，原 V2 路径保留作同轮对照。CPU 回归的结果见 `VALIDATION.json`，其结果不等于 GPU 性能验证。
